## 2. 100th-A 到底动了什么量级（设计层）

它把**每笔 VGA 突发写入扫描 FIFO 的半字数从 16 降到 8**。

问题在于：这个量在 `ddr_186.v` 里**不是 AXI 内部量**，而是作者三处非 AXI 逻辑的唯一输入：

| 消费者 | 位置 | 作用 |
|---|---|---|
| `s_prog_empty <= fifo_wr_used_words < 64` | `ddr_186.v:986` | 置位时 VGA 拿**最高**命令优先级（可长期压住 cache/CPU） |
| `s_prog_full <= fifo_wr_used_words > 350` | `ddr_186.v:983` | 置位时 FSM 停在 `2'b00` |
| **`FifoStart <= 1'b1`（`used >= 64`，只置位一次、永不清零）** | `ddr_186.v:986-990` | **直接接 `VGA_SG` 的 `.ce()`（`ddr_186.v:589`）= 扫描计数器/行场同步的总开关** |

而 `fifo` 包装（`Next186_BlackBoxes.v`）里那句注释写得最直白：

```verilog
// 【终极修复】：彻底移除复位欺骗，返回真实水量，并增加饱和防溢出截断！
// 这保证了 VGA 状态机只在真正有画面数据时才会点亮屏幕！
assign wrusedw = (full_wrusedw >= 11'd511) ? 9'd511 : full_wrusedw[8:0];
```

**量化对比（文本模式，每行 80 半字）**

| | 每行写入 FIFO | 每行消耗 | 每行净增 | FIFO 稳定区 |
|---|---|---|---|---|
| 基线（16/突发） | 160 半字 | 80 | **+80** | 64 ~ 350+（余量充足） |
| 100th-A（8/突发） | 80 半字 | 80 | **≈ 0** | **被钉在 64 这个"使能门限"上** |

⇒ 净增归零后，FIFO 水位恰好停在**"点亮屏幕"的门限附近**：任何额外时延（cache 抢占、FSM 调度）都会把它压到 64 以下。这既给出"无画面"的风险，也让 `s_prog_empty` 长期为 1（VGA 占死优先级 → CPU 饿死，与 font/CPU 侧探针全 0 吻合）。

## 3. 但"信号直接没了"这一条，我不能只用 A 解释（不掩饰）

按 RTL 推理：`FifoStart` 置位前**没有排空**——`vrdon = s_displ_on[~vga_hrzpan]`，而 `s_displ_on` 是 `displ_on = !(hblnk|vblnk|!FifoStart)` 的移位（`ddr_186.v:81/220/1402`），所以显示（也就是排空）本身要等 `FifoStart`。既然如此，FIFO 在"只进不出"的阶段必然爬到 64 并置位 `FifoStart` ⇒ **按纯 RTL 推理，A 不应该让 hsync/vsync 消失**。

所以只有两种可能，必须用测量分开：

- **(a) 还有我尚未定位的机制**（例如水位被压到门限下后 `s_prog_empty` 卡死、整片被拖死）；
- **(b) 这次 build 本身有问题**（时序未收敛 / Set Up Debug 未重建 / 编程失败 / 显示器侧）。

**判别只需一个现成探针 —— `s_prog_empty` 已经是 debug 探针（`ddr_186.v:138`）：**

- 板上 `s_prog_empty` **长期为 1 或长期不动** ⇒ FIFO 水位真的被推到门限下 ⇒ (a) 成立，A 就是元凶；
- 它与旧版一样**正常翻转** ⇒ FIFO 水位正常 ⇒ 问题不在 A，要看 (b)。

同时请对照 `dbg_cpu_ios` / `dbg_cpu_laddr` / `dbg_dbg0..5` / `dbg_sd_*` **是否有任何活动**：全无活动 ⇒ 整片没跑（build/编程问题）；只有显示没了 ⇒ 显示使能链（含 A）嫌疑最大。

## 4. 真正不可原谅的错：我的"台架验证"是无效的（三条证据）

1. **台架没有 `FifoStart` 模型**（`grep FifoStart sim/tb/ddr_pipe.v` → 无匹配）。⇒ 我改动的正是"显示总开关"的上游，而台架里这条链**根本不存在**，它永远看不到"显示没被点亮"。
2. **台架的 FIFO 水位从 512 起步**（`sim/tb/ddr_pipe.v:268` `reg [9:0] fifo_used = 10'd512;`，复位也回 512），**不是从空开始**。⇒ 台架永远不会经历"从空爬升到 64 才点亮"这个过程——而失效恰恰最可能发生在那里。
3. **我声称"把阈值降到 32"，这个补丁从未生效**：台架第 253 行的**注释**写着 `fix_100 ? 9'd32 : 9'd64`，但第 331 行的**实际代码**仍是 `s_prog_empty_m <= (fifo_used < 10'd64);`（锚点没匹配上）。⇒ 我基于一个**不存在的改动**得出了"通过"的结论。
4. 补一条：上一轮"方案 B（缩短突发）会饿死"的结论**同样不可信**——那次台架里 `vga_acc` 的清零语句也没插进去（`if (ack == 2'b10)` 锚点不存在），门一直是关着的，B 从没被真正测过。
5. 我还把 drain 参数**从 4 改到 16/32 "直到跑过"**（`fifo_drain=4` 卡死 → 16/32 通过）——这是凑答案，不是验证。

⇒ **结论：本轮"台架验证通过"、以及上一轮"B 被否决"，两个结论都必须作废。**

## 5. 两次尝试的共同根因

我把问题当成"取多少 / 喂多少"的**调参问题**，但根子是**2:1 的比例错配**（AXI 一次交付 16 半字，作者的地址只推进 8）：

- **100th-C（改地址推进量 ×2）**：动了作者的**行几何/行结束判据** `s_vga_endscanline <= (vga_lnbytecount[7:3] == vga_lnend)`（`:1062-1064`，文本模式 `vga_lnend=6`）⇒ 黑屏（且我对"为什么黑"的解释本身也未经验证）。
- **100th-A（改 FIFO 写入量）**：动了作者**流控回路的量级** ⇒ 本次。

两次都缺少同一个前提：**一个被验证过的"作者行几何 + 流控"模型**（行跨距 40、`vga_lnend=6`、使能门限 64 半字、FIFO 32 位打包、行/帧指针推进）。没有它，任何改动都是猜。

1. **确认回退生效**：重新综合回退版，看画面恢复到"有同步 + 每 8 字符重复"；同时读 `s_prog_empty` + CPU/SD 探针（见 §3 判据）。

   - `FifoStart` 的 64 门限与锁存语义；
   - FIFO 水位**从空起步**（不是 512）；按 `wrusedw` 半字单位 + 511 饱和；

3. **在两条约束下找修法**：① 不改变任何被作者逻辑消费的量的量级/节奏；② 不动作者行几何。候选方向：让 AXI 侧对 VGA **只取 `max_read+1` 个半字**（缩短突发）——这会让"取回 = 接受 = 推进"三者一致，并把 FIFO 输入量级还原成作者的原始设计值（SDRAM：每事务 8 半字）；但**必须先解决 B 的附带代价**（事务数 ×4 带来的总线开销），这正好要靠补全后的台架来量化。
4. 任何候选修法，先过"**无回归 + 两个症状复现**"双判据，再谈下板。

## 7. 教训（写成项目规矩）

1. 边界的正确表述是：**不得改变任何被作者逻辑消费的"量级或节奏"**——不只是"不改作者的文件"。`FIFE 写入量`、`地址推进量`、`可见/使能时序` 都属于此类。
2. 修"比例错配"时，**先查明这个比例在作者原始设计里的值**（SDRAM 每事务 8 半字），再让 AXI 侧**还原**它；而不是调另一个量去"凑"。
3. **台架没有对应的模型 ⇒ 不得声称"验证通过"**。台架缺什么，必须写进结论里（本轮缺 FifoStart / 水位初值 / 阈值补丁未生效）。
4. **参数"调到通过"就是没验证**。报告里出现"改成 X 就过了"必须当作红旗，回头查 X 是否掩盖了真实失效。
5. 改 RTL 前先问一句：**这个量还有别的消费者吗？**（本轮 16→8 的写入量，消费者是 `s_prog_empty`/`s_prog_full`/`FifoStart` 三个。）
