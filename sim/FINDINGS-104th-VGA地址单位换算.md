# 104th 定案：VGA 显示错乱的根因 = 移植时 `sdraddr` 单位从 **4 字节** 改成 **2 字节**，而作者 VGA 侧的常量没跟着换算

日期：2026-09-27
对照原版：`Next186_SoC-master/`（作者 Nicolae Dumitrache 的原始 SDRAM 版本）
落地脚本：`sim/tools/patch_vga_unit_rescale.py`（`--revert` 可退）

---

## 1. 一句话结论

原版一次 VGA 读 = **32 字节**，配合作者的 `vga_lnbytecount += 8`（**4 字节单位**）= 32 字节，**取回 = 记账**，自洽。
移植版把 `sdraddr` 的单位改成了 **2 字节**（CPU/cache 侧必须这么改，见 §2），**但 VGA 侧的三个常量忘了换算**：
每次读只推进 16 字节、字符行只推进 80 字节；而 AXI 侧一次读却交回 64 字节。
⇒ **交付 ≠ 记账** ⇒ 相邻事务重叠 ⇒ 屏幕"每 8 个完整字符截断并重复另外 8 个"。

---

## 2. 对照表（全部有据）

| 项 | 原版（作者） | 移植版（改前） | 依据 |
|---|---|---|---|
| VGA 读交付量 | **32 字节**（`RD1 = 8'h10` = 16 个 16-bit 字） | **64 字节**（16 拍 × 4 B） | `sdram.v`：`RD1 8'h10 // 32 bytes - cmd 10`；`ddr_186.v`：`// 10=read 32 bytes` |
| cache 填充/写回 | 64 字节（`RD2/WR2 = 8'h20`） | 64 字节（16 拍）✓ 一致 | `sdram.v` |
| sdraddr 单位 | **4 字节**：`{..., cache_hi_addr[9:0], 4'b0000}` + `PitchBits=1` | **2 字节**：`{..., 5'b00000}` + `main_araddr = 0x0800_0000 + (ram_addr<<1)` | 原版 `ddr_186.v:836`、移植版 `ddr_186.v` sdraddr 行；devmem 实测缓冲区 0x080F_0000、行距 64 B ✓ |
| VGA 读地址步进 | `max_read+1 = 8` 单位 = **32 字节** | 8 单位 = **16 字节** ✗ | 两侧同一行 `vga_lnbytecount <= vga_lnbytecount + max_read + 1'b1;` |
| 文本行步进 | `40` 单位 = **160 字节**（= 80 列 × 2 B） | 40 单位 = **80 字节** ✗ | `vga_ddr_row_col + (vgatext[0] ? 40 : {vga_offset,1'b0})` |
| `vga_lnend`（文本） | `6`，注释 **"multiple of 32 (SDRAM resolution = 32)"** = 每扫描行 **6 次** 32 字节读 | 6，但每次读只有 16 字节 ✗ | `wire [4:0]vga_lnend = (vgatext[0]|half[0]) ? 6 : ...` |
| FIFO 写门 | `!crw && sys_rd_data_valid && !col_counter[4]`（`col_counter` 装载 `2*(max_read+1)-1 = 15` ⇒ 收 **16 个半字 = 32 字节**） | **完全相同**（作者原文） | 两侧逐字相同 |

**旁证（强）**：把作者的常量按 4 字节单位代回去，文本模式显示地址 =
`2^17×4B`(512 KB 孔径) + `0xe000×4B`(224 KB) = **0xB8000** —— 正是标准 PC 文本缓冲区地址 ✓
⇒ 单位推断正确，作者整套 VGA 地址几何就是按 4 字节/单位设计的。

## 3. "每 8 个字符重复另 8 个"正好是这个错配

- FIFO 的门（作者原文）每次读只收 **16 个半字 = 32 字节 = 16 个字符单元**；
- 改前地址只推进 **16 字节 = 8 个字符单元**；
- ⇒ 相邻两次读的数据**重叠 8 个字符**，屏幕上就是 **8 个正确 + 8 个重复** ✓ 与板上症状逐字吻合。

---

## 4. 为什么我上一轮的 "B（VGA 突发改 4 拍）" 不够、且方向偏了

- 4 拍 = 16 字节，确实让它与"改前的 16 字节步进"配平 ⇒ 台架里字符流变单调（那是真的）；
- **但字符行步进仍是 80 字节、扫描行只扫 96 字节**，而真实文本行是 **160 字节** ⇒ 屏幕仍会错（台架当时没模型能看出这一点，因为台架不建模"一扫描行要多少个字符"）；
- 更根本的是：我当时把问题当成"突发太长"，而真正错的是**地址单位**。改成 4 拍等于**把交付量降到和错误步进一样小**，是把错误"配平"而不是**修正**。

**教训**：修"比例错配"必须先确定**这个比例在作者设计里的原始值**（32 字节），再让移植侧**还原**它，而不是调另一个量去凑。

## 5. 104th 修法（β）：只补"单位换算"，作者的逻辑一个字不改

| # | 文件 | 改动 | 含义 |
|---|---|---|---|
| 1 | `ddr_186.v` | `vga_lnbytecount += {max_read,1'b0} + 2'd2`（= `2*(max_read+1)`） | 步进 8 → **16 单位 = 32 字节**（= 原版 RD1） |
| 2 | `ddr_186.v` | 文本行步进 `40` → `80` | **160 字节**（= 真实 80 列文本行） |
| 3 | `ddr_186.v` | 文本 `vga_lnend` `6` → `12` | 保住"**每扫描行 6 次读 / 共 192 字节**"（6×32B，与原版同） |
| 4 | `top_zynq7010.v` | VGA 读 `main_arlen` `15` → **`7`** | 8 拍 = **32 字节** = 原版 cmd10；cache 填充仍 16 拍 = 64 字节 |

- 作者的**逻辑**（`max_read`、`col_counter`、FIFO 写门、`vga_lnbytecount` 的计数语义、`vga_lnend` 的"读次数"含义）**完全没动**；动的是**数字**，因为它们原来所在的单位在移植时变了。
- **基址不动**：孔径前缀 `6'b000001`、`17'he000/8000`、`scraddr` 派生量全部保持原样 —— 因为基址是 BIOS 按移植版映射写进去的，**已被"屏幕能显示文本"证实是对的**（这也是为什么不能用"整段 ×2"的改法：那会把显示地址整体挪走）。

## 6. 台架验证（`fix_100` 2bit：0=旧 16 拍 / 2=新 8 拍；`lnend=12 stride=80`）

```
VGA(cmd=10) AR 字节地址:  8068000 → 8068020 → 8068040 → 8068060 → 8068080 → 80680a0 → 复位
                          ⇒ 步进 = 0x20 = 32 字节 ✓  每扫描行 6 次读 ✓  扫过 192 字节 ✓
                          ⇒ 基址仍是 0x0806_8000（= 板上 VRAM 文本页）✓ 未被改动 ✓
FIFO 实收字符流:          a000 a001 a002 … a00f a010 a011 …（严格单调，无重叠）✓
FLOW:   FifoStart=1, lvl 60~366, s_prog_empty 高占比 53/37996 = 0.14%, underruns=0  ✓
        （与基线 0.17% 同量级 ⇒ 余量未受损）
mismatched bytes: 0 / 1024  PASS  ✓
```

**顺带的好处**：步进现在是 16 单位 = 32 字节的整数倍 ⇒ VGA 地址恒为 4 字节对齐（AXI 合法），
且作者那个"跨 SDRAM 行边界就夹小 `max_read`"的钳位**永远不会触发** ⇒ 之前记的残余风险自动消失。

**校验**：`ddr_186.v` CRLF 1506/0、begin/end 68/68；`top_zynq7010.v` begin/end 38/38；
Verilator lint 两文件 **0 真实 error**；探针仍 **38 信号 / 275 bit**（预算 300）。

### 7.3 步进验证（从当前代码常量直接算）

```
sdraddr 单位 = 2 字节（main_araddr = 0x0800_0000 + (ram_addr<<1)）
每次 VGA 读:  地址推进 2*(max_read+1) = 16 单位 × 2B = 32 字节
              AXI 交回  8 拍 × 4B                  = 32 字节
              FIFO 收下 16 个半字（col_counter 门）  = 32 字节
              ⇒ 推进 == 交回 == 收下    ✅ 三者一致
每扫描行  :  6 次读 × 32B = 192 字节   （原版同为 6×32=192 ✅）
每字符行  :  80 单位 × 2B = 160 字节 = 80 列 × 2B  ✅
显示消耗  :  640 像素 ÷ 8 = 80 格 = 160 字节 < 192 ✅（20% 余量，与原版相同）
地址对齐  :  步进恒为 16 的倍数 ⇒ 4 字节对齐（AXI 合法）
钳位      :  &sdraddr[7:3] 需 sdraddr mod 256 ∈ 0xF8..0xFF(248..255)，
              248 不是 16 的倍数 ⇒ **永不触发** ✅（旧步进 8 单位时可达 ⇒ 可能触发）
vga_lnbytecount[2:0] 恒 0 ⇒ 行尾校正项仍是 "-0"，行为不变 ✅
```

### 7.5 明确留下的残余（本次故意不动，写清楚免得当成"已修好"）

1. **图形模式（`vga13` / `planar`）仍带同一个单位问题**：`vga_lnend` 的 `11`/`21`、以及
   `{vga_offset,1'b0}` 都在作者的 4 字节单位下才有意义。按同样推导，若将来要修：
   `lnend` 应为 `22`/`42`；`vga_offset` 由 CRT 寄存器（CPU/BIOS）给出，需单独核对单位。
   **本次不改**：你的问题是文本模式，且没有图形模式的测试路径（改了无法验证）。
2. **基址类常量一律不动**：孔径前缀 `6'b000001`、文本 `17'h14000`（初值与 lcr 重载）、
   图形 `17'h8000`、`scraddr` 派生量。理由：它们由 BIOS 按移植版映射写入，
   已被"屏幕能显示出文本 / 图形地址落在页 5"证实正确；**且移植版当年确实改过基址**
   （作者原值文本是 `17'he000`，移植版写成了 `17'14000`）⇒ 说明**基址这一侧当年做过换算，
   只有"增量"被漏掉**，这也正是本节修法只动增量的依据。
3. `half`（低分辨率）/ 80 列共用同一文本分支 —— 与原版关系一致（原版同样共用 `6`），未做区分。
