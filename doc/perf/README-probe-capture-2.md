# 第二轮探针波形判读（2026-10-31 12:57，hw_ila_data_2.ila）

19 个探针全部抓到，1024 拍 @ clk_sdr 50 MHz = 20.5 µs。数据存 `ila_probe_20261031_pm.csv`。

## 一、逐拍构成：4 拍/beat 的每一拍都看清了

```
idx  state       col  rdv  fifo pfull
 10  R_PUSH_1    12   1    352    1     ← 推高半字(col 12→11)
 11  R_WAIT      11   0    353    1     ← rready=1, 等 rvalid
 12  R_WAIT      11   0    354    1     ← 握手完成, 锁存, rready 归 0
 13  R_PUSH_0    11   1    354    1     ← 推低半字(col 11→10)
 14  R_PUSH_1    10   1    354    1     ← 推高半字(col 10→9)
 15  R_WAIT       9   0    355    1
 ...
```

**4 拍 = 2×R_WAIT（握手）+ R_PUSH_0 + R_PUSH_1（推两个 16 位半字）。**

那两个 R_WAIT 是**协议开销，不是必须的**：`main_rready` 是寄存器输出，
在 R_WAIT 里置 1 后要等**下一拍**才能完成握手。若在 PUSH 期间保持 rready、
再加一级乒乓锁存，握手就能叠进推送里 ⇒ **2 拍/beat**。

实测每个突发 AR_ADDR→IDLE 跨度 **67 拍 / 16 beat = 4.19 拍/beat**（4 个完整突发全部一致）。

## 二、但这次数据证明：给 VGA 提速的收益很小

| 指标 | 实测 |
|---|---|
| `s_prog_full`=1 | **986 / 1024 拍 = 96.3%** |
| FIFO 水位 `fifo_wr_used_words` | **350 … 364**（中位 358，从不清空） |
| `s_prog_empty`=1 | **0 拍** |
| `vga_wide` | 0（窄模式/文本，符合待机） |
| `max_read` | 全程 7（边界钳位没触发） |
| `vga_lnbytecount` | 0/8/24/32/40/48 —— 步进 8 ✓，48 收行 ✓ |
| `s_vga_endscanline` | 1 次（row 58→59）✓ |
| `vga_line_reads` | 到 48 一次 ✓ 配额生效 |
| `vb_resync` | 0 次（没有相位重置） |

**VGA 预取被 FIFO 满背压卡住了 96% 的时间**，而且水位常驻在 prog_full 阈值附近、从不见底。
也就是说：**VGA 手里已经有约 7 行的余量**，fetcher 再快也只是更早撞上 prog_full。

⇒ 「窄模式吃满突发」对 VGA 的**延迟/画面**几乎没有收益，只能省 DDR 占用。
⇒ 「4 拍 → 2 拍」同理，对 VGA 也是收益有限；它真正值钱的地方是 **CPU miss**——
   CPU 是同步等 `ce` 的，一个 miss 要等满整个突发（67 拍 ≈ 33 个 CPU 时钟）。

## 三、待机波形里看不到 CPU 的瓶颈

本窗口 `crw=1`（写回）只占 9.8%，其余是 VGA 读填充（`crw=0`）。
4 个完整读突发 + 1 个写突发，没有 CPU 读 miss —— 因为待机时 DOS 在循环，
8 KB cache 全命中。

⇒ **要判断"游戏为什么慢"，必须换场景抓：跑游戏/大程序时再抓一次**，看：
- `crw` 的读/写比例（CPU 填充 vs 写回 vs VGA）
- CPU 发起的读请求在 AR_ADDR/R_WAIT 上等了多久（是否被 VGA 占着总线）
- 水位与 prog_full 是否把 VGA 饿住、反过来影响 CPU

## 四、顺带发现

水位在窗口内缓升（350→354，突发期间 352→358）。这是老记录里"净 +2/行"的现象：
取指速率略高于显示消耗，靠 `s_prog_full` 背压兜住。
**不是 bug**，但它正是当年"偶发吞掉一个突发 ⇒ 屏上 8 字符横移"的温床，
后续若出现偶发横移，先查这里。
